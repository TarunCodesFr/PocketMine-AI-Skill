# Architecture Deep Dive

This document explains the three-pillar architecture used in all medium and complex plugins generated by this skill. Read this if you want to understand *why* the patterns are what they are.

---

## The Three Pillars

```
┌──────────────────────────────────────────────────────────────────┐
│                      PLUGIN ARCHITECTURE                         │
├─────────────────┬──────────────────┬─────────────────────────────┤
│   FACTORY       │    SESSION       │    TRAIT                    │
│  (static)       │  (per-player)    │  (composition)              │
├─────────────────┼──────────────────┼─────────────────────────────┤
│ Manages the     │ Holds ALL state  │ Mixins for specific         │
│ *collection* of │ for ONE player.  │ session concerns.           │
│ objects.        │ Thin proxy to    │ PlayerDataTrait,            │
│                 │ Player; stores   │ ScoreboardTrait,            │
│ Provides:       │ only refs.       │ InventoryTrait, etc.        │
│ create / get /  │                  │                             │
│ remove / getAll │ Provides:        │ Used via PHP `use` keyword  │
│ loadAll /       │ onJoin / onQuit  │ on the Session class.       │
│ saveAll / task  │ update / persist │ Each owns its lifecycle.    │
│ / disable       │ isIdle / in*()   │                             │
└─────────────────┴──────────────────┴─────────────────────────────┘
```

## Pillar 1 — The Factory Pattern

### Why

Without a factory, plugin code eventually ends up with scattered `static` arrays in random classes, no consistent lifecycle, and no clean shutdown. A factory gives every entity type a standard contract.

### The Contract

Every factory **must** implement all eight methods:

| Method | Called From | Purpose |
|--------|------------|---------|
| `create(...)` | Game logic | Build and store a new instance |
| `get($id)` | Anywhere | Lookup by ID; returns `?T` |
| `remove($id)` | Game logic | Remove from collection |
| `getAll()` | Task loop | Iterate all active instances |
| `loadAll($plugin)` | `Main::onEnable()` | Load from storage at startup |
| `saveAll($plugin)` | `Main::onDisable()` | Persist to storage at shutdown |
| `task($plugin)` | `Main::onEnable()` | Register the 20-tick update loop |
| `disable()` | `Main::onDisable()` | Clean shutdown of all instances |

### ID Generation

For in-memory IDs (like duels), use sequential integers with gap-filling:

```php
private static function nextId(): int {
    $id = 0;
    while (isset(self::$duels[$id])) {
        $id++;
    }
    return $id;
}
```

For player-owned objects (sessions, clans), use the player's **XUID** as the key. Never use player names.

## Pillar 2 — The Session Pattern

### Why

Storing a `Player` object in an array creates a memory leak and a dangling reference after the player disconnects. The session pattern solves this by storing only strings (`uuid`, `xuid`, `name`) and recovering the live `Player` object on demand.

### The Session Lifecycle

```
PlayerLoginEvent  → SessionFactory::create($player)   → Session constructed
PlayerJoinEvent   → SessionFactory::get($player)->onJoin()
[Every tick]      → SessionFactory::task() → each session->update()
PlayerQuitEvent   → SessionFactory::get($player)->onQuit()
onDisable()       → SessionFactory::saveAll() → each session->persist()
```

### Memory Safety Rules

```php
// ✅ CORRECT — stores only a string
private string $uuid;
public function getPlayer(): ?Player {
    return Server::getInstance()->getPlayerByRawUUID($this->uuid);
}

// ❌ WRONG — dangling reference after disconnect
private Player $player;
```

### Context Tracking

The session tracks what "state" the player is in via nullable references to game objects:

```php
final class Session {
    private ?Arena  $arena  = null;
    private ?Duel   $duel   = null;
    private ?Party  $party  = null;

    public function isIdle(): bool {
        return $this->arena === null && $this->duel === null;
    }
}
```

**Never store objects that outlive the event scope as nullable properties.** The game object itself (Arena, Duel) is fine because it is managed by its factory and lives as long as the game runs.

## Pillar 3 — The Trait Composition Pattern

### Why

Without traits, `Session` becomes a 1000-line god class. Traits split responsibilities into focused, independently maintainable units while keeping them accessible via `$this` inside Session.

### Trait Lifecycle Contract

Each trait that manages its own data must implement three private methods:

```php
trait PlayerDataTrait {
    private function initData(): void   { /* Async DB load */ }
    private function updateData(): void { /* Async DB save */ }
}
// initData()   → called from Session constructor
// updateData() → called from Session::persist()
```

### Common Traits

| Trait | Responsibility |
|-------|---------------|
| `PlayerDataTrait` | Stats, ELO, wins/losses, DB sync |
| `InventoryTrait` | Per-kit custom item layouts, kit-edit mode state |
| `SettingTrait` | Toggle settings (scoreboard, hit particles, CPS counter) |
| `ScoreboardTrait` | Scoreboard builder lifecycle (spawn, update, despawn) |
| `HandlerTrait` | Setup wizard state (arena setup, duel portal setup) |

## The EventHandler Dispatcher

For complex plugins, a single `EventHandler implements Listener` routes all events. It is a dispatcher, not a processor.

```
EventHandler::onDamage()
    → Get session from SessionFactory
    → Null check (player may not have session yet)
    → Switch on context:
        inLobby()  → protect them
        inArena()  → $session->getArena()->handleDamage($event)
        inDuel()   → $session->getDuel()->handleDamage($event)
    → Post-routing cross-cutting (custom KB, hit particles)
```

**Rule:** EventHandler never contains business logic. It only routes and applies cross-cutting concerns that apply regardless of context (e.g. custom knockback always applies in duels, regardless of game mode type).

For simple/medium plugins, skip the dispatcher and use a normal focused listener class.

## The Duel Inheritance Pattern

When a plugin has multiple game mode variants, use class inheritance to encode the differences:

```
Duel (base class — all shared logic)
  ├── update()       final — drives the state machine
  ├── finish()       can be overridden for game-specific win conditions
  ├── handleDamage() base: cancel kill → call finish()
  ├── handleBreak()  base: cancel
  ├── handlePlace()  base: cancel
  ├── handleMove()   base: noop
  ├── handleConsume()base: noop
  └── scoreboard()   base: duration + ping lines
        │
        ├── Boxing extends Duel
        │     → handleDamage(): restore HP instead of kill; count hits to 100
        │     → scoreboard(): show hit count and combo
        │
        ├── Sumo extends Duel
        │     → handleDamage(): cancel. Void triggers finish() instead.
        │     → handleMove(): detect when player leaves platform
        │
        └── NoDebuff extends Duel
              → handleConsume(): allow (potions work in this mode)
```

**Override only what changes.** Every subclass calls `parent::method()` first when applicable.

## World Cloning for Instanced Games

For games that need a private world per match (duels, etc.):

```
Template worlds (stored in plugin data folder)
       ↓
On match start: WorldCopyTask (AsyncTask — recursive folder copy)
       ↓
onCompletion() on main thread: load the cloned world
       ↓
Teleport players into the live cloned world
       ↓
On match end: unloadWorld() → WorldDeleteTask (AsyncTask — recursive delete)
```

The template world is never modified. The live world is a disposable clone named `game-{id}`.

## State Machines

Every ticking game object (arena, duel) runs a state machine inside `update()`:

```php
// Use PHP enum for states — clearer than int constants
enum ArenaState: int {
    case WAITING   = 0;
    case STARTING  = 1;
    case IN_GAME   = 2;
    case ENDING    = 3;
    case RESETTING = 4;
}

// In Arena::update() — dispatches to the correct tick method
public function update(): void {
    match ($this->state) {
        ArenaState::WAITING   => $this->tickWaiting(),
        ArenaState::STARTING  => $this->tickStarting(),
        ArenaState::IN_GAME   => $this->tickInGame(),
        ArenaState::ENDING    => $this->tickEnding(),
        ArenaState::RESETTING => $this->tickResetting(),
    };
}
```

State transitions are explicit:
```php
private function tickStarting(): void {
    $this->countdown--;
    if ($this->countdown <= 0) {
        $this->state = ArenaState::IN_GAME;  // ← explicit transition
    }
}
```
